# Interface language (i18n)

The interface comes in Chinese and English (#49). In the Chinese interface, research and technical
terms stay in English and the connecting text is Chinese; which word goes where is decided in
[the glossary](glossary.md). Read it before writing or translating any text.

Settings has two separate choices, both stored per Mac in `state/<device>/settings.json`:

- **Interface language** (`ui_language`): `zh`, `en` or `system` (the default; the OS language).
  The page and the server's errors and messages follow it. Switching re-renders at once, without a
  reload.
- **Answer language** (`answer_language`): what the co-reader, the workbench assistant and the
  research-line chats answer in. `""` (default) keeps the profile's `answer_language` from
  `studio.toml`; `ui` follows the interface; `zh` / `en` pick one.

Text the app writes **into the vault** (the generated `Reading List.md`, and any generated view added
later) is in neither: it uses `[profile] vault_language` from `studio.toml` (`zh` by default, or
`en`), so both Macs write the same file. `ui` makes it follow each Mac's interface language, at the
cost of two Macs set differently rewriting it back and forth.

`STUDIO_LANG=en` (or `zh`) stands in for the OS language: the tests set it to `zh`, and it is handy
for screenshots.

## Files

```
web/i18n.js                       t(), tx(), the language switch (no imports, no build step)
web/locales/zh/<module>.json      frontend text, one file per module
web/locales/en/<module>.json
app/i18n.py                       t() for the server, the OS language, the answer language
app/locales/zh/<module>.json      server text: API errors, messages, generated Markdown
app/locales/en/<module>.json
scripts/i18n_scan.py              what is left to extract in web/**/*.js, and mistakes (see Checking)
tests/test_i18n.py                parity, placeholders, used keys exist, the scan, web/i18n.js in a JS engine
```

`GET /api/i18n` returns both languages flattened, so the browser never fetches a locale file itself
(this works the same in the desktop app's WKWebView). The server re-reads a file when it changes:
edit, reload the page, done.

## Keys

A key is `<module>.<name>`. The module is the file name, so `web/locales/zh/settings.json` with
`"title": "设置"` gives `settings.title`.

- **One module per page or component file**: `settings`, `reading`, `plan`, `ideas`, `direction`,
  `track`, `chat`, `note`, `reader`, `library`, `rmap`, ... Sessions working on different pages
  never edit the same locale file.
- **`common` is read-only while pages are being extracted.** It already holds what several pages
  need: buttons (`common.save`, `cancel`, `confirm`, `delete`, `undo`, ...), short states, relative
  times, units (`common.unit.papers` → "{n} 篇" / "{n} papers"), page names (`common.nav.*`), reading
  statuses and tiers (`common.status.*`, `common.tier.*`) and the glossary's shared terms
  (`common.term.milestone`, `term.kill_criteria`, ...; they follow [the glossary](glossary.md) and
  change with its decisions). Use them; don't add to `common.json`. A shared word that is missing
  goes into your own module file, and a later cleanup moves duplicates into `common`. Parallel
  sessions appending to one JSON file always conflict on its last line.
- **Names inside a module**: lower snake case, with dots to group related keys:
  `agent.not_installed`, `state.done`, `help.step1`. Name keys by meaning, not by the Chinese
  text (`empty`, not `queue_is_empty_text`). `_hint` is the small grey line under a label,
  `_title` a tooltip.
- **Flat files**: values are strings or plural objects; no nesting.
- Both languages have exactly the same keys and the same `{placeholders}` (the tests check).

## In the frontend

```js
import { t, tx } from "/i18n.js";

html`<label>${t("settings.title")}</label>`
t("bilingual.queued", { n: 3 })                      // "{n} 篇排队" / "{n} queued"
tx("zotero.help.step1", { link: html`<a href=${url}>${url}</a>` })   // markup inside a sentence
```

- **Never name a local variable, parameter or destructured name `t`** in a file that imports `t`
  (`const t = setInterval(...)`, `(t) => ...`, `catch (t)`): it hides `t()` and breaks only when that
  code runs. Use `timer`, `type`, `item`. The scan and the tests reject it, in Python too, and in
  `web/rmap/` for the research map's own `t` from `/rmap/strings.js` until it moves to `/i18n.js`.
- **Call `t()` while rendering**, never at module top level or in a constant: the text must be
  looked up again on every render, which is what makes a switch instant. Keep machine values in
  the constant and translate at render time:

  ```js
  const AUTO = ["off", "triage", "all"]; // i18n-keys: zotero.auto.{off,triage,all}
  AUTO.map((v) => html`<option value=${v}>${t("zotero.auto." + v)}</option>`)
  ```

- **Keys built at runtime need an `i18n-keys` comment** listing every key they can be, so the tests
  can check them: `"zotero.auto." + v` or `` `zotero.auto.${v}` `` needs one anywhere in the file
  (next to the list of values, as above); a key in a variable (`t(key)`) needs one on the same or the
  previous line. Braces expand: `zotero.auto.{off,triage,all}`. A ternary of literal keys
  (`t(ok ? "a.ok" : "a.failed")`) is checked as it is.
- **Whole sentences, not fragments**: word order differs between the languages. Put the variable
  parts in placeholders (`"{at} 的检查出错：{error}"` / `"The check at {at} failed: {error}"`)
  instead of concatenating pieces.
- **Plurals**: an object picked by `n` (a number), with `one` and `other` (and optionally `zero`):
  `{"one": "{n} paper", "other": "{n} papers"}`. Chinese needs only a string.
- **Dates and numbers**: `formatDate(d, options)`, `formatTime`, `formatDateTime` and
  `formatNumber(n, options)` use the interface language; `locale()` gives `zh-CN` / `en-US` for
  anything else in `Intl`. Never pass a literal locale (`"zh-CN"`) or none at all
  (`toLocaleDateString()` uses the OS language, not the interface's), and don't write `月` / `日` by
  hand. The scan lists these as `locale`. A machine format such as `toLocaleDateString("sv")` for
  `YYYY-MM-DD` ends with `// i18n-ignore`.
- **Server data**: text the server words (errors, provider status, reminder titles, engine names)
  comes back in the interface language it had when it was fetched. When the language changes, `App`
  re-fetches status and the model list and bumps `dataVersion`, so pages that load on `version`
  refresh by themselves. A component that loads such text itself adds `lang()` to its effect:
  `useEffect(() => { load(); }, [lang()])`.
- A component that keeps translated text in state, or renders outside `App`, can subscribe with
  `useEffect(() => onLangChange(() => ...), [])`.
- Language names are written in their own language in both files (`中文`, `English`).
- A missing key falls back to the other language, then to the key itself, with one console warning
  per key. On a development server (any port but 8770, or `STUDIO_DEBUG=1`) a key missing in both
  shows as `⟦settings.title⟧`, so it can't pass for real text.

## On the server

```python
from . import i18n

raise HTTPException(400, i18n.t("settings.bad_choice", name=k, value=v))
"## " + i18n.t("reading.view.inbox", n=len(inbox))
```

`i18n.tl("en", key, ...)` gives a fixed language; `i18n.tv(key, ...)` gives the vault language, for
anything written into vault files. Prompts take `i18n.answer_language()` (`"中文"`, `"English"`, or
the profile's value), not the interface language. A key built at runtime needs the same comment as in
the frontend: `t(f"translate.engine.{name}")  # i18n-keys: translate.engine.{deepseek,glm,google}`.

## Migrating a page

1. Pick the module name and create `web/locales/zh/<module>.json` and `en/<module>.json`.
2. Replace each Chinese string with `t()`; write the Chinese exactly as the glossary says, and
   the English as a short, idiomatic sentence (see the glossary's rules).
3. Put `// i18n: done` near the top of the file once nothing Chinese is left; from then on the
   tests fail if Chinese text creeps back in. A line that must keep Chinese characters (a regex
   that matches Chinese note text) ends with `// i18n-ignore`.
4. Check both languages in the browser: Settings → Interface language. English is longer, so look
   for overflow in buttons, chips and table headers.

Settings (`web/main.js` `Settings`, `models.js`, `bilingual.js`, `reminders.js`, the settings rows
of `zotero.js`) and `ui.js` are migrated and serve as the example.

## Checking

```bash
uv run pytest tests/test_i18n.py
```

```bash
uv run python scripts/i18n_scan.py --summary
```

```bash
uv run python scripts/i18n_scan.py web/plan.js
```

The scan lists, per file, every line of `web/**/*.js` that still has Chinese text (`text`) or a
hard-coded locale (`locale`) outside comments, so you can watch a page's count drop to zero.
It also reports errors, which the tests turn into failures: a local `t`, a key missing from either
language, a runtime key without an `i18n-keys` comment, and anything left in a file marked
`// i18n: done`. `--strict` also exits 1 if anything is left in the files you name; `--json` gives
the same report for scripts.
